# AI 生成代码专项清单

AI 生成的代码"看起来漂亮、语法正确、格式规范"，但存在系统性问题模式。审查 AI 代码时**必读**，逐类排查。其中第 4 节项目惯例类需在逐行审查**之前**先归纳项目惯例清单（见该节方法）。

## 1. 幻觉类（最高优先级）

- 调用**不存在的 API/方法/组件**：对每个新引入的依赖、工具方法、第三方库调用，搜索项目与依赖源码确认真实存在
- 引入项目未安装的依赖（对照 package.json / pom.xml）
- 使用的库版本与项目实际版本不符（如项目是 Vue 2 写法混入 Vue 3 API、Spring Boot 2 用了 3 的特性、javax 与 jakarta 混用）
- 编造的配置项、命令行参数、环境变量

## 2. 伪实现类（隐蔽性最强）

- mock/桩代码残留：`console.log` 占位、返回固定值的假接口、`// TODO: 实现` 空壳
- **假成功**：catch 异常后静默返回默认值/空对象/true，调用方误以为成功
- 硬编码返回值冒充真实逻辑（写死 id、状态、金额等）
- 只实现了 happy path，错误分支为空或 `pass`

## 3. 过度工程类

- 无必要的抽象层：只有一个实现却建接口、单处使用的"通用"工具类
- 防御性判空泛滥：对框架保证非空的值反复判空
- 为"将来可能"预留的死代码、未使用的参数与配置
- 不必要的包装/转换（多余 DTO 拷贝、无意义 builder）

## 4. 项目惯例类（AI 代码高发，"看起来正确"最容易掩盖）

AI 倾向用训练语料中的"通用最佳实践"覆盖项目本地约定——代码语法正确、单独看是"标准写法"，放进项目却打破了既有惯例。**判定惯例的唯一依据是项目存量代码的归纳，不是通用经验**：先读同包/同层的既有同类文件（改 Service 就看已有 Service，改页面就看已有页面），提取惯例清单，再对照变更逐项核对是否被打破。

- **重复造轮子**：手写项目 utils/common/convertor 中已有的工具、映射、封装方法——先搜索再下结论
- **绕过既有抽象**：项目已有基类、统一封装、公共入口被绕开（统一 Result 包装、统一异常处理器、BaseEntity、既有 Convertor/工具类被手写替代）
- **错误处理模式偏离**：项目统一走业务异常+错误码/全局处理器，AI 却随手 throw RuntimeException、返回布尔值或静默吞掉
- **分层与目录约定**：业务逻辑进错层（Controller 里写业务）、新文件放错目录、命名后缀不符（DTO/VO/Entity、XxxService/XxxServiceImpl）
- **命名与日志惯例**：方法命名风格、常量定义位置、日志用法与项目不符（项目统一 `log.info("xx={}", xx)` 占位符写法，AI 却 System.out 或字符串拼接）
- **数据访问惯例**：项目用 MyBatis-Plus Wrapper/既有 Mapper 方法，AI 却手写 SQL、混入 JPA 风格
- **校验与配置惯例**：项目统一 @Valid+注解校验，AI 却手写 if 逐项校验；配置键风格、@ConfigurationProperties 用法不一致
- **测试惯例**：测试基类、命名、断言风格与项目既有测试不一致
- 引入与项目既有方案竞争的库（项目用 axios 它用 fetch、项目用 dayjs 它用 date-fns）

**常见误判**：把"通用最佳实践"当项目惯例（如项目刻意不用单实现接口，AI 按"最佳实践"补接口）——惯例以存量代码为准，AI 的"标准写法"本身就是嫌疑对象，发现不一致时先核实项目现状再定级。

## 5. 测试类

- 断言空洞（只断言不抛异常/只验证类型）
- 只测 happy path，无边界与异常用例
- 为通过测试而弱化断言、或测试断言写的是错误行为

## 6. 叙事注释与模板复制类

AI 生成代码最隐蔽的失败模式之一：注释按"意图"组织叙事，但代码控制流与叙事脱节；同一段逻辑被复制 N 处后独立微调产生漂移；AI 复制适配"有动作"分支，容易漏掉分支组合矩阵中的格子或让分支彼此重叠。与日志/对账无关——分支矩阵问题在任何分支逻辑中都会出现，日志缺口与对账漂移只是最常见的观测窗口。

- 注释叙事先行：注释按意图描述路径（"成功路径""仅在 X 时""异常时才走到"），但控制流未按注释收敛——返回 false 的软失败不会中断 try，后续语句仍会执行。审查时注释是待验证假设，不是事实；注释与控制流不符可独立成条上报（误导性注释 🟢/🟡）
- 模板复制漂移：同一段逻辑复制到多个方法/类后各自微调，产生死变量、恒为空的集合、永不命中的分支。发现任一信号即对全部拷贝交叉核对——"看过一份"不代表其余拷贝正确
- 分支重叠：两个分支对同一条件组合都做了处理——同一副作用执行多次、同一事件日志双打、"顺序流 + 兜底 if"双保险。AI 用双写"保证覆盖"，实际是把两个分支的重叠当成了安全垫。逐组合统计关键动作执行次数；动作幂等报 💡 建议合并为单点，非幂等按实际后果定级
- 静默组合：条件组合矩阵中存在无定义处理的格子——尤其"全空/全等/无变化/都失败"这类无现成模板可抄的组合。AI 按"有动作才有分支"复制适配，最容易漏掉矩阵中的"无动作"格。"无操作"若是有意设计应显式表达（注释/日志/计数归类任一形式），静默且未声明即为命中；日志缺口、对账混入成功页通常是其外在表现。通常 🟢/💡，该组合本应有可观测结果（如对账场景）时 🟡
- 口径漂移（对账/分类结构的特例）：计数器/豁免/跳过集合与路径分类不一致——失败只打日志不改计数、某路径不入任何已知类别。这是分支矩阵不完备在分类结构上的投影，根因仍按"静默组合/分支重叠"定位，报 🟡

## 优先级提示

幻觉类与伪实现类通常构成 🔴 阻断（代码根本无法运行或行为是假的）；过度工程与项目惯例类多为 🟡（绕过统一异常处理等导致行为不一致的 🔴）；叙事注释与模板复制类通常 🟡/💡（若分支重叠非幂等且产生实际错误则 🔴）；发现真问题时可附 🎉 肯定 AI 做得好的部分。
