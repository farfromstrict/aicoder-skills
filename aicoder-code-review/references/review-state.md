# 多轮审查状态规范

本文件是 `.aicoder/code-review/review.md`（轮次台账）与 `.aicoder/code-review/lessons.md`（经验沉淀）的唯一格式与生命周期规范。轮首解析状态、轮末写回前必须按本文件执行（每轮至多加载一次，轮内不重读）。两个文件都是项目磁盘文件，跨对话持久；不存在时按首轮处理并在写回时创建。

> **默认审查不复核**：本 skill 默认审查**不读 `review.md`**（不判首轮/跟进、不核实未决项、不做决策复核/回归检测），仅在写回阶段读它以定轮次号与防覆盖。模式判定、决策复核、回归检测等**复核专用规则已移至 `review-state-recheck.md`，默认不读**——仅当用户明确要求"复审/复查/再审/核实遗留项"时启用。写回照常：本轮发现并入主条目（不并列/不空条目）、全终态压缩存根、lessons 增量入册、容量老化规则生效。

## 一、分工与分界

| | review.md | lessons.md |
|---|---|---|
| 定位 | 案件卷宗：每轮审查的每条问题实例及其状态 | 判例集：跨变更反复出现的模式、项目惯例缓存、用户决策口径 |
| 粒度 | 实例级（这条问题这轮怎么样了） | 规律级（这类问题/这个判断，长期有效） |
| 生命周期 | 跟随变更生命周期：活跃 → 存根（全终态）→ 删除（变更终结） | 长期：晋升后移除，或超容量淘汰 |

同一"不改"两边留不同层次痕迹：log 记实例、lessons 记判断。个案待办（"这行 TODO 以后要修"）不属于任何文件——那是任务管理的职责。

## 二、log 条目格式

```markdown
## 2026-11-04 · add-user-token · 第 2 轮 · 基线 a1b2c3d · 分支 feat/user-token
- R1-1 🟡 com/ 编译产物残留 | 已修复(第1轮核销)
- R1-2 🟢 测试全限定类名 ×8 | 未决（fuxi-auth-iam/src/test/java/com/cicc/ctie/fuxi/auth/iam/service/impl/UserTokenServiceTest.java）
- R1-3 💡 update 四种拒绝原因共用文案 | 决策不改：复用枚举是 admin 惯例（fuxi-auth-admin/src/main/java/com/cicc/ctie/fuxi/auth/admin/service/impl/UserTokenServiceImpl.java）
- R2-1 🟡 xxx | 未决（<相关文件相对路径>）
```

硬性规则：
- **条目头字段顺序固定**：`## <MM-DD> · <主题> · <N 轮或第 N 轮> · <统计/存根标记> · 基线 <c> · 分支 <b>`——省略不适用字段，但不调换顺序
- 问题行一行一个，格式 `编号 级别 一句话描述 | 状态`，描述一行封顶；编号 `R<轮次>-<序号>`，轮内连续
- **未决与决策不改行必须带 `（相对路径）`**——后续轮次核实与决策抑制的锚点；已修复/已失效行可不带
- **不设范围行**：匹配主键是主题+分支（主题规则见第六节；复核时的模式判定见 `review-state-recheck.md`），完整清单由 git 历史兜底
- **主题命名**（条目创建时定一次）：①用户显式命名 ②分支名剥离前缀 ③上下文工单号 ④agent 推断短名（标"临时"）；**接续轮次从被接续条目逐字复制主题**，绝不重新推断；用户纠偏后相关条目随写回统一改名
- 禁止把报告的问题说明整段抄入 log

## 三、问题状态（四种，全部以代码验证为前提）

| 状态 | 含义 | 进入条件 |
|---|---|---|
| 未决 | 已报、尚未处理 | 审查报告输出；携带进后续轮次，≥3 轮未决加"第 N 次提醒"徽标（级别不变） |
| 已修复(第N轮) | 代码核实确实已改 | 跟进轮核实 / 核销定点验证；**用户口头声明不采信**。🔴🟡 行存根化时保留明细（回归锚点） |
| 决策不改(理由) | 用户明确表态不修 | 用户表态；理由逐字记录；**存根化时明细行保留**，后续同文件同语义疑似问题默认静默抑制（复核时的推翻规则见 `review-state-recheck.md`） |
| 已失效(代码已删) | 引用的代码已不存在 | 轮首存在性检查 / 核实失败（复核时的存在性检查规则见 `review-state-recheck.md`） |

## 四、生命周期（三层；删除必须等变更终结信号）

| 层级 | 状态 | 触发动作 |
|---|---|---|
| 问题级 | 上表四种 | 决定是否携带进下一轮 |
| 条目级 | 活跃（有未决）/ 存根（全终态） | 全终态 → 压缩为存根：**统计行 + 决策不改明细行 + 🔴🟡 已修复明细行原样保留**（均带文件路径）；🟢💡 已修复与全部已失效项压缩为统计计数 |
| 变更级 | 进行中 / 已终结 | 存根删除仅当：① 用户宣告"已合并/不再审了" ② 存根超 30 天无后继轮次（届时连明细行一起删） |

**"全部终态" ≠ 轮次结束**：同一变更清零后继续开发，新轮次接续编号（存根保证 lineage）。轮首对未决项做引用文件存在性检查，文件已删 → 已失效。

存根示例：

```markdown
## 11-04 · add-user-token · 1 轮 · 全终态（2修1决策）
- R1-3 💡 update 四种拒绝原因共用文案 | 决策不改：复用枚举是 admin 惯例（UserTokenServiceImpl.java）
```

**写回合并纪律**：同一变更的全部轮次合并为一条目——本轮修复/决策数量累计进主条目统计头（决策数以明细行实数为准），**禁止追加并列条目或空条目**。

## 五、lessons 三段式与晋升

```markdown
## 犯错模式
- AI 测试代码爱用全限定类名替代 import（2 次：11-01、11-04）
## 项目惯例缓存
- admin controller 直接返回 VO，无斜杠 @RequestMapping（11-04）
## 用户决策口径
- common VO 无 JSR-303 + service 兜底校验，勿再报（11-04）
```

- **犯错模式**：审查发现即计数，写回时 +1（一轮内同模式多处表现 = 1 次，跨轮累计）
- **项目惯例缓存**：高层审查归纳的新惯例入册；后续轮次命中缓存 → 跳过存量文件重读（多轮审查最大的 token 节省点）；惯例失配（项目重构）时更新或删除
- **决策口径**：只收"这类判断"，不收个案；个案留 log

### 晋升策略（lessons → 规约层）

**流向分流**：犯错模式 → **可判定的代码规约** → 晋升 rules；**审查方法类**（写不成可执行规约，如"分支矩阵漏格子"）→ 留在 lessons，用户显式要求时晋升到 skill 内置清单（低频人工）。项目惯例缓存 / 决策口径 → **不晋升**（事实缓存与豁免语义）；惯例被违反且用户表态"必须遵守" → 由用户显式立为 rule。

**触发**：常规 = 同一模式跨轮累计 **≥2 轮**；快速通道 = 历史发现含 🔴/🟡 级 **1 次即触发**，或用户点名"这条写成规则"（视为确认）；静默期 = 同一候选最多主动建议 **2 次**（计数再 +2 时升级措辞再建议一次），之后静默。

**建议四要素 + 类别**（报告 💡 区）：规约文案（一句话可判定）；建议 level（历史发现最高级别映射：🔴→severe、🟡→important、🟢→normal、💡→minor）；目标类别（test/exception/logging/naming/security/architecture/api/db/performance/doc/misc 中判定，新类别需用户确认）；去向判定 + 写入形态预览。

**规约文件层与格式**（两级对称）：项目级 `.aicoder/code-review/rules/<category>.md`；用户级 skill `references/rules/<category>.md`；优先级：项目 > 用户 > 内置清单（同义冲突项目覆盖用户）。

frontmatter（**文件级** label）：

```yaml
---
category: test
language: java
tags: [ai-pitfall]
---
```

category 必填（与文件名一致）；language 用户级跨项目过滤用；tags 主题标签——**level 与 source 不是 frontmatter label，它们是条目级属性**。

条目格式（**条目级** label）：

```markdown
## [normal] 测试代码禁止内联全限定类名，依赖类一律 import

反例：`...StatusEnum state = UserTokenStateEnum.valueOf(...)`
正例：`import ...StatusEnum;` 后直接 `StatusEnum state = ...`
来源：promoted(11-04, 犯错模式 ×2)
```

分节标题 = `## [机器级别] 规约描述`（severe/important/normal/minor → 🔴🟡🟢💡）；来源行 = hand-written | promoted(日期, 源自)。

**执行流程**（用户确认后）：① 写入：追加/更新对应类别文件的分节（文件不存在连 frontmatter 创建）② lessons 对应条目删除（写入前复查目标无同义条目）③ 回执一句话（写入何处/移除何条/下轮生效）。

**写入前两查**：同义去重（扫项目 rules/*.md + 用户级 rules/*.md + 内置清单，已有同义条目 → 不写入，提示"已被现有规约覆盖"）；口径冲突（新规约与 lessons 决策口径抵触 → 提示用户裁决，默认 rules 胜）。

**补充更新**：同主题新认知到达时更新既有分节（改级别/补正反例），不新建分节。

**淘汰**：规约层（rules/*.md）仅用户主动触发（agent 永不自动删规约），发现失配只提示；lessons 侧自动老化 + 用户随时触发（见第七节）。

## 六、封存 / 解封 / 清空

| 用户说 | 动作 | 数据后果 |
|---|---|---|
| "开始新变更 X" | 全部活跃条目打「已封存(历史变更)」标记；X 从第 1 轮计数 | 无损可逆。封存条目不参与匹配与携带，轮首一行提示："log 中有 N 条已封存条目（含 M 个未决项），如相关请告知" |
| "继续改 X"（旧变更） | 解封对应条目 | 接续原编号 |
| "清空 review log" | 硬重置 | 有损：先复述将删除的内容（几条活跃/几个未决）并得到确认，才执行 |

封存 ≠ 决策不改：封存的未决项仍是"未决"。封存时若用户对遗留项表态，逐条判定去向——通用口径 → 决策不改 + lessons；纯个案 → 决策不改留 log；没表态 → 保持未决挂起。

## 七、容量与老化

- lessons 软上限 **80 行**：超限按顺序处置——① 合并同类条目 → ② 淘汰 30 天未命中条目 → ③ 仍超才淘汰最低价值条目。容量控制的目标是注意力质量，不是省 token
- log 软上限 **200 行**：超限 → 先删最老存根 → 压缩封存条目 → 提示用户清空
- 存根/封存条目 **30 天**老化删除
- **log 写回前必须重读 review.md 最新内容**（防并行会话交叉覆盖——本轮上下文里的副本可能已过期）
- review-state.md 本轮至多读一次（第 1 步），写回后不重读

## 八、轻交互（不走完整审查工作流）

- **表态**：对已报问题说"不修 / 修好了" → 打开引用位置定点核实（"修好了"必须验证）→ 更新 log 对应行；不加载清单、不出报告
- **查询**："还有几条没修 / 上次报了什么" → 读 log 回答，细节提示用户翻聊天记录
- 轻交互只碰本文件与两个状态文件

## 九、gitignore 策略

- 默认全部随 `.aicoder/` gitignore（个人工作流状态）；若 config.yaml 需提交共享 → 忽略 `.aicoder/code-review/` 但例外放行 config.yaml，此情形下条目删除改为压缩为完结摘要行（保留团队审计痕迹）
- 长期知识经晋升进入 rules/*.md，不依赖 log 被提交
